# 可调参数的仿真实验室

实验室在本机打开真实的专线应用，用 Playwright 操作多个独立司机环境；每位司机有自己的浏览器存储和待上传队列。所有乘客、密钥和 GitHub 数据接口均为模拟数据，不连接正式台账。

## 打开与使用

完成 [测试环境准备](TESTING.md) 后，在仓库目录运行：

```sh
npm run simulator
```

打开 <http://127.0.0.1:9340/>。服务需要保持运行；关闭终端或重启电脑后，重新运行以上命令即可。实验室需要本机 Node 与测试浏览器，不能直接通过 GitHub Pages 执行浏览器仿真。

1. 第一次先选「快速检查」，再点「开始仿真」。
2. 左侧修改司机人数、每人预约量、时长、速度、上传和刷新间隔。展开下方选项，可调整收款、上车、备注编辑、取消、断网与接口故障。
3. 右侧查看每位司机的实际页面快照、待上传数、云端数据量、时间曲线及请求明细。点击快照可以放大。
4. 「暂停」停止推进模拟时间，当前操作会先完成；「推进一步」按指定分钟数继续执行计划，然后停住。运行中可调速，也可停止。
5. 结束后看「自动检查」和问题列表；下载结果、请求记录、预期数据与云端数据。参数可导出和重新导入，浏览器也会记住上次参数。

四个预设分别用于日常登记、多人同时写入、弱网恢复及快速验证。修改后才开始运行；运行中的业务参数锁定，速度仍可调整。

## GitHub 额度模型

默认启用共享账号模型：5000 次 REST 请求/小时、通用内容写入 80 次/分钟和 500 次/小时，以及 900 端点积分/分钟、100 并发。GET 按 1 积分、PUT 按 5 积分近似。模型中的所有司机都使用同一个令牌所属账号的额度；不同司机、不同令牌和不同项目不会凭空增加同一账号的额度。

可以填写“开始时已用请求数”“距首次重置秒数”，测试接近耗尽与重置恢复；“其他项目请求/小时”和“其中写入/小时”会以均匀背景流量占用同一账号的预算。上限可降低以快速覆盖边界，但改动仿真数字不会改变真实 GitHub 配额。背景流量只模拟资源竞争，不向另一个真实项目发送请求。

限流返回 403/429、额度响应头及等待时间，检查应用是否提前重试。模型按照公开规则建立；二级限制采用滑动时间窗口，并保守地将获准执行的 PUT 尝试（含冲突）计入写入量。GitHub 内部窗口、各端点例外、动态风控与全局仓库锁并未完整公开，因此不能称为 GitHub 服务的精确复制，也不能把模拟最大人数当作生产容量承诺。大文件响应切换、真实网络质量和完整权限行为也不在此模型内。

参考：[GitHub REST 限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[官方请求最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)。真实配额以请求响应头为准。

## 多条专线的隔离与估算

当前正式应用固定使用 `liziyaaa/dashi-shuttle-data`，本机数据键为 `dashi-shuttle:v1`，连接键为 `dashi-shuttle:connection:v1`，离线缓存以 `dashi-shuttle-` 开头。**不能直接复制当前代码作为第二条独立专线**：同一浏览器内，同一 `liziyaaa.github.io` 来源下的项目路径不会隔离 localStorage 和 Cache Storage，可能串用数据或清理对方缓存。桌面应用的系统存储分区行为可能不同，也不能依靠图标或路径保证隔离。建立新专线时需要分别配置私有数据仓库、本机存储键、缓存前缀以及应用身份/名称；已有记录需要迁移，不能通过清空存储解决。数据隔离后，属于同一 PAT 账号的 API 预算依然共享。

仅按 120 秒刷新一次估算，10 位一直打开应用的司机每小时约产生 300 次活跃台账读取；还要加仓库检查、上传、归档和冲突重试。若每位司机持续有改动，每 30 秒一批，10 人理论上可能产生约 1200 次写入尝试/小时，通用内容写入限制可能早于 5000 次总请求触发。实际请求以测试报告和服务响应为准；不能只用 `5000 ÷ 刷新次数` 推算可用人数。

## 可重复压力测试

保持实验室服务运行，再运行 `npm run test:stress`。完整矩阵依次覆盖 5 人/30 笔与100条历史、10人/100笔、20人/200笔、弱网离线与丢响应、共享账号耗尽后重置、持续耗尽下本机保留、跨司机编辑、WebKit跨日与归档。仅运行部分场景可用 `npm run test:stress -- daily weak reset`，可选键见 `scripts/stress-lab.mjs`。

额外的 `npm run test:stress -- batched` 保留20人200笔的相同业务负载，只将上传间隔改为120秒、刷新改为300秒，用来比较合并等待与请求消耗；它不包含在默认八场景中，也不会改正式应用的间隔。

结果保存到忽略的 `simulation-results/stress-时间/`，每轮详细记录仍在实验室历史列表中。`profiles.json` 保存实际参数，`results.json` 保存验收与计数。记录的实际运行秒数属于本机仿真耗时，不是 GitHub 响应性能。持续耗尽场景的验收要求是“明确报告未同步、所有新增及修改保留在本机、不提前重试”，不会将它包装成自动同步通过。

打开 <http://127.0.0.1:9340/stress> 可查看最近一批的可视化汇总，点击场景名称进入详细结果，再点「载入这轮参数」即可修改并重跑。固定批次链接使用 `/stress?batch=stress-时间`。

## 参数含义

| 参数 | 含义 |
| --- | --- |
| 司机人数 / 每人预约条数 | 1—20 位司机；每人 1—30 笔，每轮最多 200 笔新预约 |
| 业务时长 / 开始时间 | 最长模拟一天，按北京时间生成预约、推进应用定时器，可跨日 |
| 时间速度 | 1—6000 倍的目标速度；点击、页面渲染与请求处理仍耗真实时间，实际速度受电脑性能限制 |
| 批量上传 / 自动刷新间隔 | 分别为 1—600 秒、5—1800 秒；仅替换本轮本机服务响应中的常量，不修改正式应用默认值 |
| 收款 / 上车 / 备注 / 取消比例 | 对每笔新增预约按概率安排真实页面操作；并非保证恰好有该百分比的数量，实际覆盖次数会显示 |
| 由其他司机编辑 | 备注编辑中选择其他司机操作的概率；须先收到记录，否则重试并最终报告未覆盖 |
| 断网比例 / 起点 / 时长 | 选择部分司机，断网期间继续登记；最迟在业务结束前恢复。非零比例至少选择一位司机 |
| 联网重开 | 关闭页面后在同一独立存储环境重新打开，验证本机队列恢复 |
| 延迟 / 服务错误 / SHA 冲突 / 丢响应 | 分别模拟真实毫秒延迟、503、409、服务已保存但响应丢失；多人并发本身也可能产生 SHA 冲突 |
| 每 N 请求限流 / 等待秒数 | 0 关闭额外限流；其余周期性返回 429，冷却时间按模拟时钟计算 |
| 自动收尾观察 | 业务操作结束后继续让应用自行运行，不强制点击同步；应结合上传、刷新、限流等待时间设置 |
| 手动恢复检查 | 自动不一致后，另行点击立即同步再观察；独立记录结果 |
| 历史预约条数 | 预置 45 天前的虚构旧记录，触发应用真实月归档逻辑；核对历史记录仍完整 |
| 随机种子 | 重复相同场景计划；预约 ID、实际并发与网络完成顺序可能变化 |
| Trace / 视频 / 快照 | 分别保存操作回放、每位司机视频、前 6 位司机实时快照；更多司机仍参与执行与检查 |
| 真实运行上限 | 最长 30 分钟；暂停也计时，到期保留部分结果并报告中断 |

## 如何判断问题

预期值来自计划中实际执行的业务意图，逐项核对日期、班次、方向、地点、电话、人数、票价、付款、上车状态和备注。还会核对云端缺失或多余记录、各手机与活跃台账是否一致、待上传队列及计划执行数量；预期实收与云端实收单独展示。金额内部使用分，页面显示元。

自动检查失败时，即使手动恢复成功，这轮仍显示问题。未发生计划中的离线预约、其他司机始终未收到待编辑记录等情况，会显示覆盖不足。主动停止或运行中断不能算完整通过。

并发编辑采用正式应用的整条记录“较新修改覆盖旧修改”规则。多个司机分别修改同一笔预约的不同字段时，如果某个业务意图被覆盖，实验室会报告字段差异；应结合日志判断这是当前合并规则的限制还是程序错误。缩短收尾观察期也可能发现尚未收敛的状态，不能直接推断数据永久丢失。

## 保存与回放

每轮文件位于仓库下 `simulation-results/run-…/`，已从 Git 忽略：

- `summary.json`：参数、检查结果、覆盖情况、曲线采样与最近日志。
- `requests.json`：最多 20000 条接口请求记录。
- `expected.json` / `cloud.json`：预期业务记录与最终模拟云端记录。
- `driver-N-trace.zip`：启用 Trace 时保存，可用 `npx playwright show-trace <文件路径>` 打开，查看操作、页面快照及网络。
- `driver-N-video/*.webm`：启用视频后保存，可在页面文件链接中打开。

重启实验室会载入最近保存的结果；实时页面快照仅保存在当前服务内存中。大量视频会占用磁盘，需要时自行清理 `simulation-results` 下不再保留的运行目录。

## 范围与验证

这套仿真使用实际 UI、定时器、本机队列、同步合并和月归档代码，覆盖登记、收款、上车、改备注、取消、离线恢复及可控接口故障。它不测试 GitHub 的真实容量和限额，也不能替代 iPhone 真机键盘、系统自动填充、PWA 更新或长期后台挂起测试。模拟数据不代表真实运营负载。

运行 `npm run test:lab` 可检查控制页面本身：暂停与单步、离线预约与重开、故障不能误报通过、停止保存、WebKit 归档、间隔注入及 Trace/视频产物。逻辑检查包含在 `npm test` 中。
